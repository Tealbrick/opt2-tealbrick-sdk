# Tealbrick SDK: architecture

State: verified against the repo on 2026-10-17. Claims cite paths in this repo. Anything not verified is marked UNVERIFIED. For the whole system see `engineering/ARCHITECTURE.md` and `engineering/SYSTEM-OVERVIEW.md` in the private repo `Tealbrick/opt2-tealbrick-docs`.

## 1. `@opt2-tealbrick/manifest` (crypto and decisions)

- **Sealing** (`seal.ts`): AES-256-GCM, 12 byte IV, blob `{v:1, alg, kek, iv, ct, tag}`, AAD `tb:seal:<purpose>:<record id>` so a blob cannot move to another record. `TB_KEK` is exactly 32 bytes (base64url 43 chars or hex 64 chars); anything else throws. Key id `kek_` + first 16 hex of sha256. `TB_KEK_PREVIOUS` opens old blobs; `needsReseal` drives the reseal. The doc comment about SHA-256 reduction of long values is stale: the code throws.
- **JWS** (`jws.ts`): sign and verify with required `typ`, `aud`, `iss`, lifetime caps; 30 s skew; 4 MiB document cap; external signer support for offline root signing; replay guard.
- **Key sets** (`keyset.ts`): `portalRootKeys(channel)`, `signKeySetStatement`, `verifyKeySetStatement`, `trustedPortalKeys`, `isPrivateInternalUrl`.
- **Tokens** (`tokens.ts`): verify and sign grants, call proofs (op, hook, bridge-op), tickets, slices, configs, pairing codes, agent sessions, release index.
- **Decisions** (`decision.ts`): `gate()` for the bridge (paused, grant, CRUD, audience, scope type, workflow) and `authorize()` for the app (paused per slice, grant, scope access, hold by hook, hold family, caps, money always held). `ANY_GRANT_OPS` are `tb.hold_status` and `tb.holds_pending`.
- **Other shared rules**: `dropPrivileges` (root to uid 1000, used by the SDK, `tb-exec` and the bridge), `sdkMajorOf` (0.x counts as major 1), `requiredBridgeVersion` and `BRIDGE_FEATURES`, `MIN_BRIDGE_FREE_WF` 0.1.19 and `MIN_SDK_FREE_WF` 0.1.16, `deriveIdempotencyKey`, `tagsMatch` (an empty `anyOf` passes nothing; **do not use 0.1.15**), `isValidLaunchPath`, `hookResponseProblem`, `reduceBeforeChain`, cron helpers with IANA time zones, manifest validation and digest.
- Vocabularies (`vocab.ts`) are re-exports from the spec package. They are declared once.

## 2. `@opt2-tealbrick/miniapp-sdk` (runtime)

`defineApp({manifest, handlers, hooks?, dynamic?, publicRoutes?, migrations, backup?, events?, onStart?, onStop?, jobs?, pendingCount?, attention?})` then `startApp(app, process.env)`. Boot refuses an invalid manifest, a handler set that does not match the ops (exactly one handler per non-dynamic op), or an invalid migration set.

- **Store**: one SQLite file `TB_DATA_DIR/app.db` (`node:sqlite`, WAL). SDK tables `tb_*`: meta, receipts, idempotency, scope instances, scopes, scope defaults, agents, sessions, used jti, keys, audit, secrets, jobs, cap usage, migrations. Apps never open their own database.
- **Migrations**: `migrations/NNNN_name.sql` or `.ts`, forward-only, gap-free from 0001, one transaction each, sha256 recorded. A changed, missing, misnamed or `down` migration stops boot with `migration_invalid`.
- **Receipts and holds**: ONE table, `tb_receipts`. A hold is a receipt row. Statuses: run, held, approved, denied, refused, failed, after_failed. Raw input is never stored (`inputDigest` only). One approval per call: repeat the same call within 15 minutes of the decision; matched by (caller, op, inputDigest); consumed once. Pending TTL 15 minutes (max 24 hours); expiry denies with `decidedBy: "expiry"`.
- **Hold view binding** (0.1.23, 0.1.24; 0.1.33 the default view is JSON in JCS key order, so a permuted-key replay matches its approval): see `engineering/ARCHITECTURE.md` section 3.4 in the docs repo. Code: `src/server/ops.ts` (`dynamicHoldText`, `defaultHoldView`, `holdViewDigest`, `HOLD_VIEW_UNREADABLE`); test `test/hold-view.test.ts`.
- **Scopes**: manifest `scopes[]` with `defaultGrants` (own, shared, all) applied on first sight of an agent. Effective access is `grant.crud ∩ op.crud ∩ scope access`, except that (0.1.35, C283 A1) a row the owner wrote with `tb.scopes_set` (`authority: "owner"`) is primary for a scoped op, also above the Portal grant's crud; every other row (`authority: "bounded"`, the default, and every row that existed before SDK schema 8) keeps the grant as its ceiling. (0.1.36, C283b/C283c) An owner row keeps the CRUD it was set with: `crud_snapshot` is the level's crud at write time, the effective crud (`ScopeGrantRow.crud`, one helper `rowCrud` in `scopes.ts`) is snapshot ∩ the level's crud now, and a widened level shows as `offer.adds` until the owner accepts it with `tb.scopes_set` `acceptOffer {adds}`; test `test/owner-authority.test.ts`. Rows carry `source` (`default`, `owner`, `app`), `authority` and `grantedByOp`. (0.1.31) A live person op may call `ctx.scopeGrants.grant/revoke` (one agent, one instance, bounded by the agent ceiling = the highest level `defaultGrants` give agents; `scope_grant_invalid`); a live agent call may call `ctx.scopeSelfRevoke`. Code: `src/server/scopes.ts` (`scopeGrantOps`), `ops.ts`; test `test/scope-grants.test.ts`. (0.1.32) A live person op also gets `ctx.companionCallers()` (frozen copies of the CURRENT slice `companionCallers`, `[]` when the slice is stale; undefined on agent, app, scheduled and job contexts) and an app caller's `ctx.caller.listed` says whether the current slice still lists it under its verified product (SPEC-GAP spec 0.1.49). Code: `ops.ts` (`personCompanionCallers`, `buildContext`), `trust.ts`; test `test/companion-callers.test.ts`. (0.1.37, C292) Every op context (and the start, event and job-handler contexts) gets `ctx.bridgeCaps()`: a frozen copy of the CURRENT slice's `bridge.caps` (`[]` when the slice is absent, expired or has none), advisory only, never read for authorization. Code: `trust.ts` (`bridgeCaps`), `ops.ts` (`buildContext`); test `test/bridge-caps.test.ts`. (C373, spec 0.1.80) The same contexts get `ctx.topology()`: a frozen deep copy of the CURRENT slice's `topology` (workspace grant picture in tuple form, sent only to a `needsTopology` app with the owner's `topology` consent), `null` when absent, expired or malformed, rows with an out-of-range index dropped (`truncated: true`), with `agentIds` of the same slice read so `agentIdx` resolves without a race, display only, never read for authorization. Code: `topology.ts` (`readTopology`), `trust.ts`; test `test/topology.test.ts`.
- **Model roles** (0.1.40, C322(3)/C330(4), spec 0.1.64; `@opt2-tealbrick/manifest` `src/model-roles.ts` re-exports it and mirrors the unreleased follow-up constants): manifest `settings.modelRoles[]` (M-MR-1..5) declares roles per consumer (`app` or a `tb-exec` service); `modelRole(role)` resolves one with `GET /tb/v1/model-roles/<role>` (instance assertion, cache per `keysRev`, `null` for unset/below policy, `role_undeclared` before any request); a required role in force that does not resolve makes readiness `needs_keys` with attention `model_role_missing`; `tb-exec` fills the env named by `modelRoles[].env` for its service (every proxy variable stripped after that, M-MR-4 refuses `MODEL_ROLE_DENIED_ENV` names) and restarts the child on a `keysRev` change; a paused workspace or instance makes `modelRole()` and `getKey()` throw `paused`; conformance row `A23.model_role_no_route` (RM-17). Code: `src/server/model-roles.ts` (wired by `keys.ts`), `src/exec/roles.ts`; tests `test/model-roles.test.ts`, `test/exec/tb-exec.test.ts`.
- **Caller context and app hold status** (0.1.41, C367 P3/P4, spec 0.1.77; `@opt2-tealbrick/manifest` `src/caller-context.ts`): `callApp(..., { context })` sends `CallEnvelope.context` only with the bridge cap `app_call_context` (`bridge_cap_missing` otherwise) after the shared `callerContextProblem` check; the target stores the caller product's keys as `meta.callerContext` on an app caller's receipts (informational only, never read by `authorize()`, approval match or idempotency) and `tb.holds_pending` shows `callerContextSummary` computed at read time; `tb.hold_status` answers an app caller only for holds it raised (`404 hold_not_found`, the agent's unknown-id answer, otherwise). Code: `src/server/ops.ts` (`callerContextOf`, `receiptMetaWithContext`), `src/server/link.ts`, `src/server/receipts.ts`; test `test/app-call-context.test.ts`.
- **App events** (0.1.38, C274c/C274d, spec 0.1.57): `ctx.emit` / `ctx.purgeEvents` write one row of the transactional outbox `tb_event_outbox` (SDK schema 11) on the same connection, so a row shares only its transaction's fate; scope-row narrowing writes purge rows and hold decisions write `tb.hold.decided` in their own transaction; a background sender drains the outbox in id order to `POST /tb/v1/events` only while the slice declares the `events` cap, computing `eligible` of a scoped event at send time (slice agents only, ≤ 500); committed rows only, a batch ends after a purge, 413 halves the batch, and 10 failed sends in a row raise attention `events_send_failing` (order: backup → events_send_failing → app → jobs). Code: `src/server/events.ts`, `scopes.ts` (`rowsOn`, `noteChange`), `receipts.ts` (`onHoldDecided`); test `test/events.test.ts`. The shared declaration, payload and grant helpers live in `@opt2-tealbrick/manifest` (`src/events.ts`).
- **Keys**: `getKey(name)` prefers an app-own key (sealed in `tb_keys`) over the bridge's account default (`GET /tb/v1/keys/<name>`). Without a required key readiness is `needs_keys`.
- **Secrets**: `ctx.secrets {put, get, delete}` sealed under `TB_KEK`, excluded from export, sealed inside backups. The one app-secret mechanism (C31).
- **Backups**: cron from the manifest, `tb-backup-<UTC>.tar.gz` (`tealbrick.backup/1`) with `app.db` (VACUUM INTO) and per-service dumps through `tb-exec`; restore with `TB_RESTORE_FROM` at next boot (every part hash checked); export `tealbrick.export/1`. Instance key and KEK are never archived. Health carries backup status; the SDK raises attention for invalid, never, failed or overdue backups.
- **Status loop**: `POST <TB_BRIDGE_URL>/tb/v1/status?wait=60` with readiness, versions, scopes revision, slice revision, keys revision, `pendingHolds`, `attention`. A slice older than 12 hours makes ops answer 503 `slice_stale`; the person UI stays up.
- **Routes the SDK mounts**: `/tb/v1/ops/:op`, `/tb/v1/hooks/:hookId`, `/tb/v1/bridge/{catalog,resolve,mark,scope-summary}`, `/tb/v1/manifest`, `/tb/v1/openapi.json`, `/tb/v1/health`, `/a/<product>/tb/launch`, `/a/<product>/tb/v1/{session,logout,ops/:op}`, UI static, declared public routes.
- **Person session**: cookie `tb_session` (32 random bytes, sha256 stored, `Path=/a/<product>/; HttpOnly; Secure; SameSite=Lax`, 8 hours) and CSRF header `TB-CSRF`.
- **Privilege drop**: a process that starts as root chowns the volumes to uid 1000 and drops before opening files, keys or listeners. A mount-point guard refuses to claim an identity on ephemeral disk (L9).
- **Jobs** (0.1.21): `ctx.jobs` (leased, resumable ticks with checkpoints), `ctx.schedule` (scheduled ops re-authorized at fire time), `onStop`. Types are local to the SDK, not in the spec package.
- **Companion calls**: `ctx.callApp(product, op, input)` goes through the bridge; an undeclared op throws `companion_undeclared` before any network call; `grant_stale` or `grant_expired` re-reads the slice and retries once.
- **`tb-exec`**: wrapper entrypoint for companion containers. Claims as a service, fetches declared keys, spawns the upstream process with them as env, control port 7077 (backup and restore). Drops privileges only if the service opts in (C54). **`tb-gen`**: deterministic `openapi | kit | docs | railway | check | all`.

### Upgrade-safe boot (0.1.25, E2)

Boot order: scan migrations, restore from `TB_RESTORE_FROM` if set, open, refuse data newer than the code (`app_schema_newer`, `sdk_schema_newer`), then, if a migration is pending or the app version changed, take the migration lock (table `tb_migration_lock`, 120 s lease; a second instance waits up to 150 s, then `migration_locked`), write a pre-update snapshot (`TB_BACKUP_DIR/tb-preupdate-to-<version>.tar.gz`, backup `kind: "preupdate"`, newest 3 kept, never listed by `backups.list()`, `preupdate_snapshot_no_space` when free space is under 2x the database, an interrupted upgrade reuses its snapshot), then migrate with a heartbeat per file in one `tb_meta` transaction. New `tb_meta` keys: `app_version`, `schema`, `min_compatible_code`, `min_compatible_sdk`, `upgrade_in_progress`, `last_preupdate`. **Failed mode:** any failure in restore, open, schema, lock, snapshot or migrations no longer exits (no Railway crash loop). `GET /tb/v1/health` answers 200 `FailedHealth {status: "failed", failure, attention, schemaVersion, codeSchema, minCompatibleCode, preUpdateSnapshot}`; `/tb/v1/manifest` is served; every other route answers 503 `app_failed`; a claimed instance pushes status `degraded` with the failure every 15 s. **Restore checks** refuse before replacing anything: `product_mismatch`, `version_newer`, `schema_newer`. A restored database drops the lock row. No new environment variable names. Code: `src/server/upgrade.ts`, `failed.ts`, `backup.ts`, `app.ts`; test `test/upgrade.test.ts`. Core's side is E3 (see `engineering/ARCHITECTURE.md` section 2.8 in the docs repo).

## 3. `@opt2-tealbrick/conformance`

`tb-conformance app|manifest|core|bridge|relay`. Fakes (Portal, bridge, upstream) are generated from the spec and the manifest and must derive from the SDK's shared rules, never from the side under test (L1). The catalog has 558 distinct check ids with spec 0.1.31 (per group: manifest 21, app 124, bridge 252, core 154, relay 10 = 561; three ids, `C8.env`, `C5.portal_key_rotation` and `cred.p1.payload_scan_no_person_cred`, are in both the app and bridge groups). Waivers are dated and per check id (`--waive <id>@<untilVersion>` or `tealbrick-conformance.json`), covering only while the suite version is below `until`. Test roots are passed in `TBCONF_PORTAL_ROOT_KEYS`. Since 0.1.20 the app target can also run REAL peer apps (`--peers`, group X, CONF-MULTIAPP): released apps from the signed release index (source at the recorded commit, frozen install, build) behind the fake bridge, each with its own fake bridge in one shared world; see `packages/conformance/README.md`. Conformance is not release evidence: QA is. Note: the package also depends on `miniapp-sdk` for the `real_app` bridge group (an intentional exception not in `CONFORMANCE.md`).

## 4. Template

`create-tealbrick-miniapp` writes a working app: manifest with one read op, one write op and one scope type, `src/`, a React UI, migrations, skills, Dockerfile, CI files, Apache-2.0 `LICENSE`, `NOTICE` and `THIRD_PARTY_NOTICES.md`. The Dockerfile pattern is two stages on `node:24-slim` pinned by digest, `pnpm install --frozen-lockfile --ignore-scripts`, build, prune, `ENV TB_DATA_DIR=/data TB_BACKUP_DIR=/data/backup`, `USER node`, no `VOLUME`. Template pins lag the repo today (SDK 0.1.19, conformance 0.1.16, ui 0.2.3).

## 5. Known gaps

- Package pins: manifest, miniapp-sdk and conformance pin spec 0.1.57 (dist tarball; run `node ci/tb-ci.ts pin-tarballs` after every pin change so the lockfile has integrity).
- `PORTAL_ROOT_CHANNEL` is hard-coded to `"dev"` in `packages/miniapp-sdk/src/server/trust.ts`. A stable build needs production roots.
- Template pins lag (SDK 0.1.19, conformance 0.1.16, ui 0.2.3); its CI copies were moved to ci-v9.9.
- `packages/conformance` defines the only `conformance` script: `gen:check` (sdk-exports table) plus `test/app-suite.test.ts`, `test/coverage.test.ts` and `test/manifest.test.ts` (via `scripts/run-tests.ts conformance`). The CI `conformance` stage (`tb-ci.ts run conformance`, which runs the root `pnpm run conformance` script) and `pnpm conformance` run them. The package's `test` script runs all its other test files, so the `unit` stage does not repeat them.
- Licence: every package has `LICENSE` (Tealbrick Software Licence) and `NOTICE`, and declares `"license": "SEE LICENSE IN LICENSE"`; versions released earlier stay MIT (see `LICENSING.md`). The `create-tealbrick-miniapp` template keeps its own Apache-2.0 `LICENSE` for generated mini apps.
