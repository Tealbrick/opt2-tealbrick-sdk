# @opt2-tealbrick/miniapp-sdk

Server runtime for opt2 miniapps (SDK-API §3–§13): `defineApp({ manifest, handlers, hooks?, dynamic?, publicRoutes?, migrations, onStart?, onStop?, events?, jobs?, attention?, pendingCount? })` + `startApp(app, process.env)`. The SDK mounts every route from the manifest (`/tb/v1/ops/:op`, hooks, bridge ops, person session under `/a/<product>/`, health), verifies grants and call proofs, runs `authorize()`, owns the one store (node:sqlite under `TB_DATA_DIR`), receipts/holds, idempotency, scopes (manifest default grants), audit, keys (`getKey`: app-own > workspace default via the bridge), app secrets (`ctx.secrets`, sealed under `TB_KEK`), claim via the bridge, slice refresh, `callServiceHelper`, and (0.1.21) the ONE background job runner: `ctx.jobs` (leased, resumable ticks with checkpoints, retries, pause/resume/cancel per job and per app, restart drain) and `ctx.schedule` (scheduled ops that re-run `authorize()` at fire time with the stored caller). Apps do not write their own schedulers (SDK-API §19). (0.1.23, SDK-HV-1) A dynamic op may add `holdView(tool, args, ctx)`: the SDK awaits it (5 s budget) when a call is held and shows its plain-text view to the owner; a failure shows the default view plus "Tealbrick could not read the content of this request." and never blocks the hold; the approval is bound to sha256(view), so a changed upstream content is held again (SDK-API §4.6). (0.1.24, C202) Content that cannot be read at the retry never runs on an approval: it is held again (fail closed). (0.1.25, E2 / UPGRADE-SAFETY M1–M3) Upgrade-safe boot: before any pending migration or app-version change the SDK takes ONE migration lock per database (`tb_migration_lock`, 2 min lease, a crashed holder is taken over) and writes a pre-update snapshot `TB_BACKUP_DIR/tb-preupdate-to-<version>.tar.gz` (backup format, meta `kind: "preupdate"`, `version` = the data's version, `schema`; newest 3 kept; fails closed when the volume has less than 2 × the database free). A failure in restore, schema check, lock, snapshot or migrations no longer exits: failed mode serves `GET /tb/v1/health` (200, `status: "failed"`, `failure {phase, code, file?, reason?}`, attention) and pushes readiness `degraded` + attention to the bridge. Data newer than the code is refused explicitly (`app_schema_newer`, `sdk_schema_newer`); health and the status push carry `schemaVersion {app, sdk}`, `minCompatibleCode` and `preUpdateSnapshot`. `TB_RESTORE_FROM` refuses another product, an archive from a NEWER app version or an archived database at a newer schema before replacing anything; for a pre-update snapshot it skips the restore when the data is at the snapshot's schema (data kept) or when the snapshot is missing and the data is runnable.

0.1.1 adds: backups/restore/export (§7.3, ustar+gzip, cron), the React client (`@opt2-tealbrick/miniapp-sdk/client`: `TbProvider`, `useSession`, `useHolds`, `useScopes`, `useAgents`, `tbFetch`, `callOp`), and the `tb-exec` bin (`tb-exec [--manifest <path>] [--helper-cmd "<cmd>" --helper-target 127.0.0.1:<port>] -- <upstream...>`; default manifest path `/opt/tb/tealbrick.manifest.json`).

0.1.3 adds the `tb-gen` bin: `tb-gen openapi | kit [--build] | docs | railway | check | all [--manifest <file>] [--out <dir>]` — generated from the manifest, deterministic; `check` is the drift check (CONFORMANCE M4).

## 0.1.43 (C373, G-2; spec 0.1.87): `ctx.topology()`

- **`ctx.topology(): SliceTopologyView | null`** (`SliceTopology & { agentIds: readonly string[] }`) on every op context and on the start, event and job-handler contexts. It is a deeply frozen copy of the CURRENT verified slice's `topology` in its compact tuple form: `{v: 1, instances: [ins, product, name, version][], edges: [agentIdx, instIdx, crud, mode, held, wfCount, paused][], companions: [fromIdx, toIdx, crud, opsCount][], connections: [con, agentIdx, method, status][], truncated?}` (CORE "v0.1.80"). `agentIds` = the agent ids of the SAME verified slice in slice order, read together with the topology (one slice read): resolve `agentIdx` as `agentIds[agentIdx]`, never against another read of the agents (a newer slice may reorder them, and `agentsChanged` does not fire on a pure reorder). `held` is a bitmask over `MANIFEST_HOLD_FAMILIES`.
- **Indexes.** A row with an index out of range is dropped and the copy says `truncated: true`; the other rows stay.
- **null** when the slice is absent, older than 12 h, has no `topology`, or the topology is malformed (`v` not 1, wrong arity, a value outside its type, a list over `TOPOLOGY_MAX`); it never throws.
- Core sends it only to an app whose manifest declares `needsTopology: true` (with `needsAgentDirectory: true`, M-TP-1) and whose owner granted the consent `topology` (MANIFEST §9).
- **Display only.** Never authorize with it; the grant decides. Nothing in the SDK reads it for authorization (`test/topology.test.ts` pins the files that may name it). It is stale until the next slice revision.
- SPEC-GAP until the spec pin carries 0.1.80: `SliceTopology`, the tuple aliases and `TOPOLOGY_MAX` are exported from this package as mirrors of `@opt2-tealbrick/spec/bridge` (`src/server/topology.ts`); they switch to the spec import with the re-pin (the decode helpers `topologyCrudActions` / `topologyHeldFamilies` come from the spec).

## 0.1.41 (C367 P3 + P4; the number is a reservation, the release lead assigns it at merge): `callApp` context, `tb.hold_status` for app callers (spec 0.1.77)

Needs `@opt2-tealbrick/manifest` 0.1.32 and spec 0.1.77 (re-pinned). Both features are gated by a bridge cap (`app_call_context`, `app_hold_status`); without the cap nothing changes.

- **`callApp(product, op, input, { idempotencyKey?, context? })`** in every ctx (op, start, event). `context` undefined or `{}` = no context (not sent, no cap needed). A non-empty one: `companion_undeclared` first, then `bridge_cap_missing` (409, `details: { cap: "app_call_context" }`) when `ctx.bridgeCaps()` lacks the cap, then `input_invalid` (400, `details.pointer`) from `callerContextProblem(<own product>, context)`; all before any network call. ## 0.1.40 (C322(3), C330(4)): model roles — `modelRole(role)`, readiness, `tb-exec` env (spec 0.1.63 mirror)

Needs `@opt2-tealbrick/manifest` 0.1.31 and spec 0.1.64 (a superset of 0.1.63; re-pinned; the bridge side is BRIDGE §15.4, the answer type `ModelRoleFetchResponse`).

- **`modelRole(role)`** on `OpContext`, `StartContext`, `HookContext`, `JobContext`, `KeyApi` (`rt.keys`) and as a free export → `Promise<ResolvedModelRole | null>`. `GET <bridge internal>/tb/v1/model-roles/<role>` with the instance assertion (same client and auth as a key fetch). 200 → the binding without `keysRev` (a copy; never log it, never return it in an op result: the key joins the log redaction registry). 404 (`role_not_set`; also a bridge without the route, a 404 with no refuse code = a bridge without cap `model_roles`, RM-17: fail closed, a required role then gives `needs_keys` + `model_role_missing`, never a guess and never a fall back to keys) and 403 `role_policy_too_low` → `null`. The app uses a stored model (an embeddings index's model) only against the endpoint and key resolved now: the SDK drops every cached binding when `keysRev` changes. Any other refusal (`paused`, a malformed answer) throws with the bridge's code (`model_role_unavailable` for a malformed answer) and is not cached. A role the manifest does not declare with `usedBy` `app` throws `role_undeclared` (500) before any request; a declared role whose `when` is false (settings read as for keys) returns `null` without a request.
- **Cache per `keysRev`.** A binding (and a `null`) is kept until the `keysRev` the SDK knows changes (`keysRev` is one revision for keys and bindings), on a pause, or for ever when it never changes; nothing is cached (and nothing marked resolved) before the claim, when there is no bridge client yet; one in-flight fetch serves concurrent calls; an error is not cached. `onKeysChanged` fires for a binding change too (with the names of the changed `account_default` keys: `[]` when only a binding changed), after the role cache already reads the new revision.
- **Pause (C349).** With the workspace or this instance paused in the verified slice, `modelRole()` and `getKey()` throw `paused` (503/403 shape `TbError`) even if the bridge would answer 200 (an undeclared role still throws `role_undeclared` first), the role cache is dropped, and the owner text never says `Model role not set` while paused. A paused edge agent is read from `agents[].status` (C353: `pause.agents` is `[]` in app slices).
- **Readiness.** While a `required: true` role with `usedBy` `app` whose `when` holds does not resolve (unset, below `minPolicy`, bridge unreachable, not asked yet), `health()` is `needs_keys` and the status push carries `attention {code: "model_role_missing", reason: "Model role not set: <roles>. ..."}` naming only those roles; both clear when it resolves (a status is pushed when the set changes). ONE attention slot (SDK-API v0.1.63 as amended by specs#49): any attention that is not a model-role code (a backup code, `events_send_failing`, the app's own fault, a job fault) is reported and `model_role_missing` / `model_role_optional` / `embeddings_changed` are not; model codes show only when nothing else is wrong (the SDK's `model_role_missing` first, then the app's own model code). Order of faults: backup, events, app, jobs; readiness stays `needs_keys` while a required role is missing. Optional roles never block: the app decides (`defineApp({attention})`, `model_role_optional`, `embeddings_changed`). The existing key readiness logic is unchanged.
- **`tb-exec`.** A service that a role lists in `usedBy` with `env` gets each role resolved with the service key at start (together with its keys); `provider`, `model`, `baseUrl`, `key` and `dims` (as a string) go to the named env vars, a value that is null sets nothing, an unset optional role sets nothing and the upstream starts. The child restarts when the delivered values change on a new `keysRev` (as for keys; an unchanged value does not restart it). tb-exec strips EVERY proxy variable from the env of a role-bound service (any name ending in `_proxy` in any case: HTTP_PROXY, GRPC_PROXY, PIP_PROXY, SOCKS_PROXY, GLOBAL_AGENT_HTTP_PROXY, NODE_USE_ENV_PROXY ...; plus `npm_config_*proxy`), AFTER the key and role env went in (a proxy would resolve the name itself); M-MR-4 refuses such names as role env names, with every name of `MODEL_ROLE_DENIED_ENV` (spec follow-up #54: loader, library-injection, TLS-trust and config names). A REQUIRED role in force that does not resolve blocks the upstream like a required key (status `needs_keys` + `model_role_missing`; re-pulled with backoff and on every `keysRev`); a role whose `when` names a setting the service's env does not carry is asked for but never blocks.

## 0.1.38 (C274c, C274d): app events — `ctx.emit` and the outbox (spec 0.1.57)

Needs spec 0.1.57 and `@opt2-tealbrick/manifest` 0.1.30 (validator reads `events`; shared event helpers). Release order (MANIFEST §16.3): spec 0.1.57 → manifest 0.1.30 → miniapp-sdk 0.1.38 → conformance 0.1.28 → bridge 0.2.7 (the first bridge that declares the `events` cap); Core and the CI template re-pin manifest ≥ 0.1.30 before any app release declares `events`.

- **`ctx.emit(name, data, {subject, to?, instanceId?, summary?, untrusted?, key?})`** on op, event, start and job-handler contexts (SDK-API §20). Synchronous: it validates (TbError 400 `event_undeclared`, `event_reserved` for any `tb.*` name and for every emit of a manifest `tb`, `event_payload_invalid`, `event_too_large` — `data` > 2 KiB JCS, `summary` > 280, or the whole wire item without `eligible` > 4 KiB, e.g. a long `to` list — `event_instance_invalid`, `event_target_invalid`), then INSERTs one row of the outbox `tb_event_outbox` (SDK schema 11) with the raw handle of the SAME connection. The row shares only the fate of the transaction that is open: rolled back → gone; committed → sent, also when the handler throws later. Emit and change state in one `ctx.db.transaction`. Default key = a new ULID made at emit (not the row id); `untrusted: true` is copied; `causedBy` = the verified agent caller of the op (never app code; absent for persons, apps, events, start and jobs).
- **`ctx.purgeEvents(instanceId)`**: one all-agent purge row (call it in the transaction that deletes or disconnects the instance). The SDK writes `purge {agent, instanceId}` itself, in the transaction of the row change, when an AGENT row of ANY scope type is removed, its effective crud narrows, or it goes from owner to bounded (`tb.scopes_set`, the store's `set`, `ctx.scopeGrants.grant/revoke`, `ctx.scopeSelfRevoke`): an app update may have removed the event while older events of it are still stored. A level narrowed by an app update writes nothing (no row change).
- **`tb.hold.decided`** to the hold's AGENT caller (never an app caller) on approve and deny (in the decision's transaction) and from the expiry sweep: data `{holdId, op, decision: approved | denied | expired}`, subject `{kind: "hold", id}`, no summary.
- **Sender** (SDK-API §20 with the specs#33 sender rules). Background; sends only while `ctx.bridgeCaps()` includes `"events"` (by capability, C292) and only COMMITTED rows: it never reads or deletes while a transaction is open on its connection. Batches of ≤ 100 rows in id order (and under 480 KiB) to `POST <TB_BRIDGE_URL>/tb/v1/events` with the instance assertion (htm, htu, bd); no emit follows a purge in one batch (consecutive purges may share one), so a lost answer and a retry never re-send a purge ahead of a later event. A 200 must answer every item with the item's own key, in order: stored / duplicate / refused (logged with its code) → the row is deleted; anything else (transport error, 401, 429, 5xx, 503 `app_not_claimed`, a short or reordered 200) → the whole batch again with backoff 1 s … 60 s (same keys). 413 → the batch is halved and sent at once, down to one item; one EMIT still answered 413 is dropped and logged `event_too_large` (it does not count as a successful send); one PURGE answered 413 is never dropped, it is retried with backoff like a transport error. The batch size doubles back only after 10 consecutive fully answered sends. After 10 consecutive failed sends (any cause) the app reports `AppStatus.attention {code: "events_send_failing"}` until a send succeeds. Woken after every emit (next macrotask, after the commit) and on every installed slice; a 30 s fallback timer; unsent rows older than 7 days are pruned (logged at info); `stop()` aborts a send in flight (its rows go again later). A scoped emit gets `eligible` at SEND time from the scope store: agent rows on (scopeType, instanceId) whose EFFECTIVE crud ⊇ visibleWith.crud, each with its authority, only agents in the current verified slice, at most 500, ∩ `to` for a target event. The emit records the event's scope type: a row whose `visibleWith` scope type changed by an app update before it was sent is dropped (logged), never sent with `eligible` computed on another type. The `summary` limit (280) counts UTF-16 code units (a JavaScript string length, BRIDGE §14.1).
- **Attention order (admin queue c / 5b; release note).** `AppStatus.attention` is picked by severity: (1) the SDK's backup attention (invalid or never-firing schedule, failed, overdue), (2) `events_send_failing`, (3) the app's own `attention()`, (4) the job attention (failed, stuck). Before 0.1.38 the app's attention came first and hid a failed or overdue backup (`pickAttention` in `status.ts`).

## 0.1.37 (C292, C292a): `ctx.bridgeCaps()` (spec 0.1.54)

Needs spec 0.1.54 and `@opt2-tealbrick/manifest` 0.1.29 (re-pin of spec 0.1.54, no behaviour change: its slice check reads only `bridge.id` and `bridge.keys`, so it accepts the new `bridge.caps` member). ## 0.1.36 (C283b/C283c owner rows keep their CRUD; C268 B hook proof `bd`; spec 0.1.52)

Needs `@opt2-tealbrick/manifest` 0.1.28 and spec 0.1.52. Release order (C215): spec 0.1.52 → manifest 0.1.28 → miniapp-sdk 0.1.36 → conformance 0.1.25 → bridge 0.2.5. **Apps go from SDK 0.1.34 or older straight to 0.1.36** (skip 0.1.35): no app shipped 0.1.35, so no owner row exists that the migration below cannot read.

- **An owner row keeps the CRUD it was set with (C283b/C283c, SDK-API §7.2).** `tb.scopes_set` by the owner stores a snapshot of the level's crud in the manifest that runs at write time (`tb_scopes.crud_snapshot`, a JSON array, NULL on bounded rows). The effective crud of an owner row (`ScopeGrantRow.crud`, `rowCrud` in `scopes.ts`) is that snapshot ∩ the level's crud NOW: a narrowed level applies at once, a widened level does NOT apply. A NULL, unparsable or non-array snapshot on an owner row, and a level the manifest no longer has, give `[]` (fail closed). ONE helper feeds every reader: `resolve` (one instance and best access), the best-row order, `ownerAdmits`, `ctx.scope` `access.crud` / `readable` / `writable` / `can`, `scope_summary` `admittedOps`, the dynamic catalog `admitted` mark, `ScopeGrantRow.crud`. Bounded rows are unchanged (the level's crud now; the Portal grant stays the ceiling).
- **Offer and accept.** A row whose level now grants more than the snapshot lists `ScopeGrantRow.offer: {adds}` (in `tb.agents_list`, `useScopes().access`, the store). **The owner UI MUST show `offer.adds` and call `useScopes().acceptOffer(agent, type, instanceId, adds)` only on an explicit owner click**: the SDK cannot prove that a person clicked (C283b (4)). `acceptOffer` sends `tb.scopes_set` with the row's own level and `acceptOffer: {adds}`. The SDK accepts when the level is unchanged and `adds` equals the current `offer.adds` as a SET (any order, duplicates ignored): new snapshot = the level's crud now, audit `scope.offer_accepted`. Another set, or any adds when there is no offer (only `[]` is accepted: a no-op), is 409 `offer_changed`; `acceptOffer` with another level or `access: null` is 400 `input_invalid`. A plain re-set of the same level without `acceptOffer` keeps the snapshot (it does NOT accept); another level stores that level's crud now. No agent, app, companion or `ctx.scopeGrants` path accepts: they write bounded rows (and clear a snapshot).
- **Migration (SDK schema).** `sdk_scope_crud_snapshot` adds `crud_snapshot TEXT` and, in the SAME transaction, backfills every owner row ONCE from the manifest that runs it, with one audit `scope.snapshot_backfill` (level + crud) per row. The migration runner has a code step for it (`SdkMigration.after`); `startApp` and a restore pass the running manifest. After the backfill a NULL snapshot on an owner row means `[]` (corruption or a bug never widens). A widening shipped in the SAME update as the first 0.1.36 boot is baked in (no older record exists). The spec text calls this "schema 9"; schema 9 is `sdk_receipt_admitted_by`, so the migration is **version 10** (`SDK_SCHEMA` 10). A rollback to an older SDK without a restore is refused `sdk_schema_newer`; an E3 restore of a schema 9 backup re-runs the migration on the retried update.
- **Hook proof `bd` (C268 B/C268c).** The hook route reads the raw body bytes, hashes them (`sha256`), then `JSON.parse`s the SAME bytes (an empty or non-JSON body is 400 `input_invalid`; the shape checks run after). A hook proof that carries `bd` is refused 401 `call_proof_invalid` unless it equals that digest; a proof without `bd` is accepted. The SDK declares `proofClaims: ["bd"]` in its claim and in EVERY status push (also failed mode); the bridge (0.2.5) sends `bd` only to an app that lists it.
- **Client.** `useScopes()` returns `acceptOffer(agent, type, instanceId, adds)` next to `set`.

### Also in 0.1.36 (earlier notes)

- **Scheduled-op fire reads the op's `listing` (C283b item 2).** `fireScheduledOp` now passes the op's `listing` to `opInGrantWorkflow`, exactly like `gate()`: an op with `listing: "workflow"` fires only when the grant's `wf` names it, in any mode. Before, an agent with a Free grant and an empty `wf` could schedule such an op and it ran at fire time, while a live call of the same op was refused `not_in_workflow`. Now the fire is refused `not_in_workflow` (refused receipt, handler never runs). Ops without a `listing` are unchanged.
- Tests: four gaps from the sdk#34 review. A stored scope authority that is not exactly `owner` (other case, other text, NULL) reads bounded (G1); a scheduled fire refuses `caller_unverified` (G2) and reads the scope row's authority like a live call, so a bounded row never lifts the stored grant (G3); `scope_summary` and the catalog mark nothing for an agent whose slice status is not `active` (G4). No change in `src/`.

## 0.1.35 (C283 A1): the owner-set access row is primary (spec 0.1.50, C277)

Needs `@opt2-tealbrick/manifest` 0.1.27 (`authorize()` honours `access.authority`; `gate()` skips the CRUD ceiling for scoped ops) and spec 0.1.50. Release order (C215): manifest 0.1.27 indexed and mirrored, then miniapp-sdk 0.1.35, then conformance 0.1.24.

- **The rule.** For a scoped op the effective crud of an agent (or app) caller is the crud of the row its app holds for it. A row the OWNER wrote with `tb.scopes_set` from a verified person session is `authority: "owner"` and applies even above the Portal grant's `crud` (a narrower owner row still narrows). Every other row is `authority: "bounded"`: effective crud = `grant.crud ∩ row.crud`, as before. Ops without a `scopeType` keep `op.crud ⊆ grant.crud`. Pause, revoke, expiry, the workflow binding (`wf`), held families, caps and `money` stay Portal-grant rules: an owner row never revives a paused or removed agent and never skips a hold or a cap.
- **Who writes an owner row.** ONE path: `tb.scopes_set` on the person route (session + CSRF). It also sets `owner` when the access level is unchanged: that is how the owner makes an existing row primary ("make primary" is offered by the app's owner UI, never applied by the SDK). EVERY other write is `bounded`, also when it overwrites an owner row: manifest `defaultGrants` (they never overwrite an existing row), `ctx.scopeGrants.grant` (a person-op app row), and the store handle that `startApp` returns (`running.scopes.set(...)`): that handle is app code's own and the principal it takes is a plain object, so it records source `owner` as before but authority `bounded`. `ctx.scopeSelfRevoke` and `ctx.scopeGrants.revoke` only delete. An agent op and an app (companion) call can reach none of the owner path: `tb.scopes_set` is person-audience (agent and app callers get 403 `audience_not_agent`), and the owner write is not a member of the store object.
- **Resolve.** `ScopeAccessView.access.authority` and `ScopeGrantRow.authority` (also in `tb.agents_list`) are always `"owner"` or `"bounded"`. For an op that spans instances (the handler's `scope` returns `null`) the best access is used and the authority is `"owner"` only when EVERY row the caller has for that scope type is an owner row (fail closed: one default or app row anywhere makes it bounded).
- **Migration.** SDK schema 8 `sdk_scope_authority` adds `authority TEXT NOT NULL DEFAULT 'bounded'` to `tb_scopes` (forward-only, additive, no value rewritten). Every row that exists at the upgrade is `bounded`, also a row with `source = 'owner'`: such a row was written while it could only narrow access, so it must not widen it now. The owner opts in per row by saving it again. SDK schema 9 `sdk_receipt_admitted_by` adds the nullable `tb_receipts.admitted_by`. Both are covered by the pre-update snapshot like every SDK migration. A database that already ran schema 9 cannot be opened by an older SDK (`sdk_schema_newer`): restore the pre-update snapshot to go back.
- **Receipts.** `Receipt.admittedBy` (`"app_owner_row"` for an owner row, `"portal_grant"` otherwise) on every receipt, hold and approved hold of a SCOPED op that passed the scope step; absent on unscoped ops, refusals and rows from before 0.1.35. A hold records the rule that admitted it at hold time; the run after approval records the rule that admitted the run.
- **Bridge display (spec 0.1.50, display only; the SDK authorizes every call).** The catalog bridge op reads the optional `agent` of the body: an entry gets `admitted: "owner"` iff that agent is in the verified slice, active and not paused, and its owner rows admit the entry's `crud` for the op's scope type (every row an owner row, best row's crud). A value of `admitted` that the app's own catalog put on an entry is dropped. `scope_summary` adds `admittedOps` per agent: the static agent ops with a `scopeType` whose crud its owner rows admit (absent when none; nothing for a paused or removed agent).

## 0.1.35 (C261 = C243): `caller_unverified` for an app caller without a verified product (spec 0.1.49)

- **The rule.** When the verified instance slice carries `appCallers: "verified"` (Core sets it exactly when it mints the grant `prd` claim for every companion grant to this instance: bridge 0.2.3 or newer), the SDK refuses an app (companion) call whose caller has no verified product, that is no `prd` in its grant and no `companionCallers` entry for its instance: 403 `caller_unverified`, `details.retryable: true`, message "the calling app is not verified for this workspace yet: update the bridge, or retry after the workspace config refreshes". The check runs before anything else of the call (input validation, standard ops such as `tb.hold_status`, scope defaults, idempotency key, cap slot, handler), so nothing runs and nothing is created for the caller. The refusal is audited as a `refused` receipt (`meta.reason: "caller_unverified"`, op, caller, no product).
- **Resumed held calls.** An approved hold is used when the agent or app repeats the call; that repeat is a call like any other, so a caller that lost its verified product between the approval and the repeat is refused and the approval is NOT consumed (it runs once the caller is verified again). A scheduled op fire of an app caller applies the same rule (`refused` `caller_unverified`); a fire already needs the caller to stay in `companionCallers`, so this is defence in depth there.
- **Retryable.** The flag and the product are read from the CURRENT slice at every call: the same call runs as soon as a newer slice lists the caller (or the grant carries `prd`).
- **Unchanged.** Without the flag, or with any value other than the exact string `"verified"`, an unverified app caller runs with `ctx.caller.product` absent as before. Agent and person callers are never affected. Handler jobs (`ctx.jobs`) run no `authorize()` and are not affected.

## 0.1.35 (C268 A): the hook proof must name the caller and the call of the hook request

Needs `@opt2-tealbrick/manifest` 0.1.27 (`verifyHookProof` with `sub` and `call` bindings). The hook route (`POST /tb/v1/hooks/<id>`) compares the proof `sub` with the caller ref of `body.call.caller` (`tb:agt:<id>` for `type: "agent"`, `tb:ins:<id>` for `type: "app"`) and the proof `call` with `body.call.id`. A mismatch, or a body without a usable caller or call id, is 401 `call_proof_invalid` and the hook handler does not run; the one-time proof is not used up by a mismatch. Bridges that sign hook proofs as the spec describes (`sub` = the caller, `call` = the hook request id) are unaffected. The body digest part (C268 B, `bd`) is not in this release.

## Default hold view from JCS (0.1.33, G7, C275, fix)

- **Fix.** The default view of a dynamic hold (`holdView` answers `null`) is the op title plus the input as indented JSON in the JCS key order (RFC 8785, the same `canonicalize()` as the input digest). Before 0.1.33 it kept the caller's key order, so a replay of the same input with its keys in another order (another client, a JSON round trip) gave another view hash: the approval was not used and the call was held again (`approval not used: the hold view changed`). Now the same input always gives the same view and hash; a changed value is still a new hold, and an approval still runs exactly once. Views the app returns from `holdView` are unchanged (the app owns their text).
- **Upgrade note.** A hold that is pending or approved while the app updates from 0.1.32 or older to 0.1.33 can be held one more time on its replay (its stored view text has the old key order); the owner approves it once more. This happens once per such hold. New holds are not affected.

## Scope grants from a person op (0.1.31, SDK-INSTANCE-GRANT, spec 0.1.47)

A person op can give ONE agent access to ONE scope instance, in the same op the owner just confirmed (for example "start this draft and let agent X work on it"):

```ts
run: async (input, ctx) => {
  await ctx.scopes.instances.create("project", id, label);
  if (!ctx.scopeGrants) throw new TbError("not_a_person_op", "owner only", 403); // undefined on agent and app calls
  const row = await ctx.scopeGrants.grant(agentId, "project", id, "read_write"); // the stored ScopeGrantRow
  // later: await ctx.scopeGrants.revoke(agentId, "project", id);
}
```

- **Where it exists.** `ctx.scopeGrants` is set ONLY in a live person op (verified session + CSRF). It is `undefined` on agent calls, app (companion) calls, scheduled fires, hold views, public routes and Start/Event contexts. `ctx.scopeSelfRevoke(type, instanceId)` is set ONLY on a live agent call and removes the calling agent's OWN row (narrowing is always allowed; audited as `scope.set` with the AGENT id as actor and `source: "agent_self"`). Both closures work only while the op runs: they stop when the handler promise settles, on the 30 s timeout and on a client disconnect, and a later call (a closure kept in a global) throws 409 `scope_grant_expired`. The write paths are not members of the scope store object that Start/Event contexts hand to app code.
- **Bounds (else 400 `scope_grant_invalid`, `details.reason`).** `agent_invalid`, `type_unknown` (not a manifest scope type), `instance_unknown`, `level_unknown`, `no_agent_ceiling`, `above_ceiling`, `agent_not_in_slice` (the agent must be in the current verified slice = have an edge to this app) and `agent_paused` (agent status not `active`, or the agent, this app or the workspace is paused in the slice). The decision reads the CURRENT slice; an expired slice (older than 12 h) answers 503 `slice_stale`.
- **The agent ceiling.** The manifest has no per-level "agent allowed" marker, so the ceiling of a scope type is the HIGHEST access level that any `defaultGrants[]` entry gives AGENTS (`callers` absent or containing `"agent"`; order: more CRUD actions first, then manifest order). A level may not be above it in that order and may not carry a CRUD action the ceiling lacks. A type whose defaults reach no agent has no ceiling: the app cannot grant it (fail closed). Example: defaults `own: read_write` and levels `read`, `read_write`, `manage` (same CRUD as `read_write`): `read` and `read_write` are grantable, `manage` is refused.
- **The row.** The same row `tb.scopes_set` writes (`tb_scopes`), with `source: "app"` and `grantedByOp` = the person op id; an existing row for the agent and instance is replaced. Audited as `scope.set` with the person principal, `{type, instance, access, source: "app", op, callId (null: a person op has no call id), requestId}`. `revoke` removes the agent's row for the instance whatever its source (owner, default or app) and audits it; no row, no audit.
- **Sources.** `ScopeGrantRow.source` is `"default"` (manifest `defaultGrants`), `"owner"` (`tb.scopes_set`) or `"app"`, and `grantedByOp` for `"app"`; both appear in `tb.agents_list` and `ctx.scopes.list/access`. A forward-only SDK migration (`sdk_scope_source`, SDK schema 7) adds the nullable columns `source` and `granted_by_op`; rows written before 0.1.31 keep NULL and report NO `source` (the writer was not stored and is not guessed). Nothing is rewritten and the migration is never destructive (pre-update snapshot as for every SDK migration).
- **Known limits (documented, not changed).** The ceiling ignores the KIND of the default grant (`own` vs `shared` / `all`): a level that only a `shared` default gives agents still counts. A revoke does not stick across a share toggle: an instance that becomes shared gets the `shared` default again for agents seen before (`INSERT OR IGNORE`), exactly as for a revoke by the owner. No `tb_scopes` rows are removed when an agent leaves the slice.
- **Unchanged.** `authorize()` step 2 reads the row at call time; the Core grant still bounds crud, workflow and held families first; Rules hooks still run on every call. The standard Agents & scopes page lives in the app template (`packages/create-tealbrick-miniapp/template/src/ui/standard.tsx`, copied into each app) and its default list shows no scope rows; an app that renders scope rows (`AgentsPage render`) gets `source` and `grantedByOp` (op id) from `tb.agents_list`. The spec row has no grant date and no op title field, so "given by <op title> on <date>" is not renderable from the row alone (the op title comes from the manifest; the date would need a spec field).

## Companion callers on owner pages (0.1.32, SDK-COMPANION-CALLERS, spec 0.1.48)

A person op can list the verified apps that may call this app, for example to render "Connected apps" with where each one runs:

```ts
run: async (_input, ctx) => {
  const callers = ctx.companionCallers?.() ?? []; // undefined on agent and app calls
  return { apps: callers.map((c) => ({ name: c.name, product: c.product, provider: c.provider })) };
}
```

- **Shape.** `ctx.companionCallers()` returns `readonly CompanionCaller[]`: `{ product, ins, name, provider }` for each entry of the verified slice `companionCallers[]`. `provider` is where that instance runs (`"railway"`, `"own_infra"`, another provider key); a value that is not `^[a-z][a-z0-9_]{1,31}$`, `null` or an absent field reads as `null` (unknown, a Core before the field). Malformed entries are skipped, as for every other use of the slice list.
- **Where it exists.** Set ONLY in a live person op, at the same single place as `ctx.scopeGrants`. It is `undefined` on agent calls, app (companion) calls, scheduled fires, hooks, jobs, hold views, public routes and Start/Event contexts. No grant material is ever in an entry.
- **Fresh and frozen.** Each call reads the CURRENT verified slice (not a snapshot from the start of the op), so a slice update between two calls shows. The array and every entry are frozen copies: changing them has no effect on the slice. While the slice is missing or older than 12 h (`trust.stale`) the function returns `[]`.
- **Not for authorisation.** The list is display and binding data for the owner page. To decide anything per caller, key on `ctx.caller.product` / `ctx.caller.id` (verified), as before.
- **`ctx.caller.listed` on app callers (0.1.32, extension).** On an APP caller, `ctx.caller.listed` is `true` when the verified caller instance is in the CURRENT signed slice `companionCallers` under the SAME verified product as `ctx.caller.product`; `false` when the slice is stale (older than 12 h), the instance is not listed, or it is listed under another product. The key is ABSENT on person and agent callers. It is evaluated when the context is built: a live op call, a scheduled-op fire and a resumed held job each read the then-current slice. Typed in spec 0.1.49 (`Caller.listed`, the pin is 0.1.49): read `ctx.caller.listed` directly; `SdkCaller` stays exported as an alias of `Caller`. Key on `ctx.caller.product` and `ctx.caller.id` for identity; `listed` only says whether the signed slice still lists that instance.
- **Unchanged.** `Caller.product`, the `grant_revoked` check and the fire-time re-check of scheduled ops read the same slice list and behave exactly as in 0.1.31.

## 0.1.34 (C259, S4): attribute budget and parse-time bounds for `sanitizeAgentDocument`

- **Pre-parse attribute caps.** `MAX_ATTRIBUTES_PER_TAG` = 2 048 (was 256) attributes in any tag-like token, and NEW `MAX_ATTRIBUTE_BUDGET` = 4 194 304: the sum over tag-like tokens of attrs² (each `>` charges the largest count among the candidates it ends, squared; the end of the source charges the largest open count, squared). `agentDocumentStats()` adds `attributeCost`. The scan is unchanged (context-free, linear). Benign pages the old cap refused now pass: a script loop `for(var i=0;i<n;i++){ …300 statements… }`, prose `1 < 2 and a<b and …400 words`, `<style>/* a<b …400 words */</style>`.
- **Parse-time bounds** (all SDK parses: first pass, both verification passes, `fillTextSlots`), ONE implementation shared with Live Artifacts (`src/server/bounded-parse.ts`, ported from live-artifacts `src/bounded-parse.ts` @1d9c462): depth past `maxDepth` (600) stops the parse at once, a moved subtree is measured again; elements copied by the parser are charged attrs² to a budget of 4 194 304; `<html>`/`<body>` attribute merging is linear and capped at 2 048; the elements of one parse are capped at min(`MAX_ELEMENTS` = 200 000, 3 × the `<` of the source + 4 096); foster parenting and child moves are linear and their work is capped; the first-pass output is capped at max(4 × input, input + 1 MiB) and re-checked against the attribute caps. New exports: `MAX_ATTRIBUTE_BUDGET`, `MAX_ELEMENTS`, and from `bounded-parse.ts` `boundedParse`, `boundedTreeAdapter`, `ParseLimitExceeded`, `ParseBounds`, `maxOutputLength`, `PARSE_MAX_ATTRIBUTES`, `PARSE_ATTRIBUTE_BUDGET`, `PARSE_MAX_CHILD_WORK` (Live Artifacts imports them instead of keeping a copy).
- **Empty scripts (S4).** A script left with no source and no code is removed (`element:script-empty`) and does not set `runsScripts`.
- **Known limits.** See "Known limits (0.1.34)" below: repeated adoption-agency moves over-count depth (`<body>` + `<b><div><span></b>` × 350, real depth 354, fails closed).
- **Dependency.** Built with `@opt2-tealbrick/manifest` 0.1.26 (`ajv` 8.18.0, GHSA-2g4f-4pwh-qvx6); release and mirror the manifest first.
- **Tests.** Measured ceilings for pages at the limits, every known bypass shape refused in < 100 ms, a mutation check that the square matters, a seeded DoS fuzz (`TB_FUZZ_MS`, `TB_FUZZ_SEED`). Behaviour change: pages over the new bounds that 0.1.31 accepted (for example 30 000 `<html>` tags, or re-opened formatting elements that multiply the page) now fail closed.

## `sanitizeAgentDocument()` (0.1.29, C238, C230, C232; 0.1.30 needs `@opt2-tealbrick/manifest` 0.1.25; 0.1.34 C259, built with manifest 0.1.26)

Agent-written HTML is served as a sandboxed `/_d/` document. CSP cannot stop every way such a page reaches the network (`<link rel=prerender>`, `<a ping>`, a navigation), so the server removes those constructs before it serves the page. Server entry only (`import { sanitizeAgentDocument } from "@opt2-tealbrick/miniapp-sdk"`), never the browser `/client` entry.

```ts
const r = sanitizeAgentDocument(agentHtml, { allowScripts: false, assetPrefix: "/v/live-artifacts/_s/" });
// r = { ok: boolean, html: string, removed: { kind: string; count: number }[] }
```

- **Method.** Parse with parse5 (8.0.1, MIT; its one dependency is `entities`, BSD-2-Clause), walk the tree, apply `AGENT_DOCUMENT_RULES`, serialise. Never a regex on HTML. The page is always parsed with scripting ON (the conservative reading), and every `<noscript>` is removed with its content, because `<noscript>` content parses differently with scripting on and off. `<template>` content (nested, and declarative shadow roots) is walked like the rest of the page.
- **Removed in every mode (0.1.30, C238).** `<script type=speculationrules>` (a prerender and prefetch declaration, not page script) and `<script type=importmap>` (it can point module loads off-site), also with `allowScripts: true`, in any namespace (HTML, `<svg>`) and inside `<template>`. The type is trimmed, ASCII lower-cased and read without parameters after `;`; character references are decoded by the parser first. They are counted as `element:script-speculationrules` / `element:script-importmap`. JSON data scripts (`application/json`, `application/ld+json`) still follow `allowScripts`. `runsScripts` is read from the output, so a page whose only script was a speculation rules script reports `false`.
- **Removed.** `link` (every `rel`: prerender, prefetch, preconnect, dns-prefetch, preload, modulepreload, stylesheet, icon, ...), `base`, `meta[http-equiv]`, `form`, `iframe`/`frame`/`frameset`/`fencedframe`, `object`/`embed`/`applet`/`portal`, `noscript`, `<a ping>`, `srcdoc`, `xml:base`, and `target` on `a`/`area` (the link then gets `rel="noreferrer noopener"`). With `allowScripts: false`: `<script>` and every `on*` handler. With `allowScripts: true` (Live Artifacts, in its sandbox) scripts and handlers stay, and every network attribute is still checked.
- **URL attributes** (`href`, `src`, `action`, `formaction`, `poster`, `data`, `background`, `cite`, `manifest`, `xlink:href`, `attributionsrc`, ...; `srcset` and `imagesrcset` candidate by candidate): the value is read as a URL parser reads it (leading and trailing control characters and spaces stripped, tab and newline removed, character references already decoded), then it must be a `#fragment`, a raster `data:image/(png|gif|jpeg|webp|avif|bmp)` URL (never on `a`, `area`, `use`, `script`), or a path under `assetPrefix` without dot segments, `%2e`, `%5c` or a backslash. Everything else is removed: absolute and protocol-relative URLs, `javascript:`, `vbscript:`, `data:text/html`, `data:image/svg+xml`, relative paths, `java\tscript:`. A removed `href` leaves the link text. A kept URL is written back in its cleaned form.
- **CSS** (`style` attributes, `<style>` text, and the SVG presentation attributes `fill`, `filter`, `mask`, `clip-path`, `marker-*`, `stroke`, `cursor`, ...; SMIL `to`/`from`/`values`/`by`): a declaration that uses `url(`, `image(`, `image-set(`, `cross-fade(`, `element(`, `src(` (any case, any vendor prefix such as `-webkit-image-set(`), `@import`, `expression(` or `-moz-binding` is removed, after CSS escapes are decoded (`\75 rl(`) and with comments read both as a separator and as removed. `url(#fragment)` is the one allowed `url(`. A bad rule prelude removes its whole block; a bad presentation attribute is removed. SMIL elements (`set`, `animate`, `animateTransform`, `animateMotion`) whose `attributeName` is `href` or `xlink:href` (or an `on*` handler) are removed. A `<style>` that holds markup (SVG namespace) is removed.
- **Output.** Starts with `<!-- tb:sanitized v1 -->` (once). Pages that hold nothing to remove come back byte-equal except for the marker, when the input is already in the serialiser's own form (`parse5` writes double-quoted attributes, no `/>` on void elements). `removed` lists a rule kind and how many times it fired (`element:link`, `attribute:ping`, `attribute:url:href`, `css:declaration`, ...); never the removed content.
- **Fail closed.** On a parse or internal error, an input over 2 MiB (UTF-8 bytes; the viewer body cap), a tree deeper than `maxDepth`, a page over the pre-parse caps (more than `MAX_ATTRIBUTES_PER_TAG` = 2 048 attributes in any tag-like token, a sum of attrs² over the tag-like tokens above `MAX_ATTRIBUTE_BUDGET` = 4 194 304, or more than `MAX_TAGS` = 100 000 tags; see below), a parse past a parse-time bound (depth, elements the parser copies, `MAX_ELEMENTS`; see below), an output longer than max(4 × input, input + 1 MiB), a bad option (`assetPrefix` must be a path like `/v/live-artifacts/_s/`), or an output that a second pass would still change, it returns `{ ok: false, html: AGENT_DOCUMENT_UNAVAILABLE_HTML, removed: [] }`: a fixed inert page ("This file cannot be shown.") that echoes no input. After the first pass the output is parsed again with scripting on and off; each re-parse must remove nothing and give the same text. So sanitising twice equals sanitising once, and a parser differential (mXSS) ends in the inert page, not in a live construct.
- **Pre-parse caps (DoS).** parse5 checks duplicate attributes quadratically, so one tag with 36 000 attributes costs seconds. Before any parse, `agentDocumentPrecheck(html)` (linear, exported with `agentDocumentStats`, `MAX_ATTRIBUTES_PER_TAG`, `MAX_ATTRIBUTE_BUDGET` and `MAX_TAGS`) scans the WHOLE source with no notion of comments, raw text, CDATA or `<script>`: every `<` that could start a tag (`<` + letter, or `</` + letter) starts a tag-reading automaton at that point, whatever the page "really" is there (inside `<!-->`, `<!--->`, `--!>` closers, an SVG `<style>`, a MathML `<title>`, a `<textarea>`: all counted, a hiding trick can only add candidates). The automaton follows the HTML tokenizer's tag states (names, quoted and unquoted values, `/`), so a `>` in a quoted value does not hide attributes, and automata in the same state are merged keeping the highest count, which keeps the pass linear. The count for any real tag is one of the candidates', so it is never below what parse5 will see (tested against parse5 on random tag soup, and on 21 hiding variants of a 36 000 attribute tag, which must reach zero parser calls). The caps (0.1.34, C259): no tag-like token over 2 048 attributes, and `agentDocumentStats(html).attributeCost` = the sum over the tag-like tokens of attrs² at most 4 194 304 (= 2 048²: a whole page may cost what one tag at the hard cap costs; parse5's duplicate check is quadratic per tag). How a token is charged: each `>` that ends one or more candidates charges the largest of their counts, squared (real tags never overlap, so at most one real tag ends there); the end of the source charges the largest count still open, squared, so a token that never closes is charged too. These replace `AGENT_DOCUMENT_RULES.maxAttributesPerTag` (256), which the SDK no longer reads. Over the caps: `ok: false`, the inert page, no parse. `fillTextSlots` applies the same caps (and the 2 MiB limit) before it parses, and returns the inert page over them. Any later re-parse of agent HTML (data binding, templating) must call `agentDocumentPrecheck` first. Tests inject a counting parser (`sanitizeAgentDocument(html, opts, { parse })`, a test seam) and assert zero calls, never a wall-clock race. The 36 000 attribute pages are generated in `test/agent-document.test.ts` (180 KB each) rather than stored in the corpus.
- **Parse-time bounds (0.1.34, C259).** Every parse the SDK makes (the first pass, both verification passes, and `fillTextSlots`) goes through the bounded parse5 tree adapter of `src/server/bounded-parse.ts` (the same logic as Live Artifacts; the header of that file lists each bound with the shape that cost seconds without it) and fails closed DURING the parse, not after it: (1) depth: each element gets a recorded depth on insertion and past `AGENT_DOCUMENT_RULES.maxDepth` (600) the parse stops at once (60 000 nested `<div>`: 10 s before, ~6 ms now); a subtree the parser moves (adoption agency, foster parenting) is measured again when it lands deeper, so a recorded depth is never below the real one; template content counts one level BELOW its template (the post-parse walk counts it at the template's depth, so a page with nested templates at the limit is refused one level earlier); the post-parse depth check stays. (2) Copies: an element the parser copies from an earlier tag (a re-opened formatting element, an adoption agency clone) is charged attrs² against a budget of `MAX_ATTRIBUTE_BUDGET` for the parse (`<p><b a0..a255>` + `<p>x` × 20 000: a 39 MB output in 15 s before). (3) `<html>` / `<body>` attribute merging: an incremental name set (parse5 rebuilds one per tag: quadratic), the element capped at 2 048 attributes, its growth charged to the budget (`<html zN>` × 30 000: 26 s before). (4) Elements: at most min(`MAX_ELEMENTS`, 3 × the `<` of the parsed source + 4 096) per parse. (5) Sibling lists: a foster-parenting insertion point is searched from the end of the child list and every search and shift is charged against 2^24 entries of work (parse5's default adapter does `indexOf` from the front: `<table>x<b></b>` × 32 000 cost 0.6 s per parse); the adoption agency detaching a long block child by child (99 000 `<br>` inside `<b><div>`, 12 s) is charged the whole list each time and is refused. The output of the first pass must be at most max(4 × input, input + 1 MiB) long and within the attribute caps before it is parsed again. `deps.parse` (test seam) receives the bounded adapter in `options.treeAdapter`; a seam that replaces it bypasses (2)-(5). The wall-clock tests (`test/agent-document.timing.ts`) and a seeded DoS fuzz (`test/agent-document.fuzz.ts`; `TB_FUZZ_MS`, default 60 s in CI and 5 s locally; `TB_FUZZ_SEED`) run alone after the unit tests (`npm test`); the fuzz requires every input to be checked or refused within 250 ms + 3 × the slowest linear rate measured at start × its length, and sanitising twice to equal once. Known linear cost: CSS text is the slowest path (~0.4 µs per character on the dev Mac: a 2 MiB style sheet takes ~0.75 s).
- **Known limits (0.1.34).** A recorded depth is never lowered when the parser moves a node to a shallower place, so repeated adoption-agency moves over-count: `<body>` + `<b><div><span></b>` × 350 (real depth 354) fails closed (tested as a known false refusal). Accepted: fail closed, only pathological pages. Pages that 0.1.31 accepted but that exceed a new bound now fail closed (more than 2 048 merged `<html>`/`<body>` attributes, copied elements over the attribute budget, more elements than the cap, more child-list work than 2^24 entries, an output longer than max(4 × input, input + 1 MiB)). Context-free counting stays: 5 000 white-space-separated words after a `<`+letter in a script, comment or text with no `>` read as one tag over 2 048 attributes.
- **Empty scripts (0.1.34, S4).** A `<script>` (HTML or SVG) that is left with no `src`, `href` or `xlink:href` after the URL rules and no code (no child, or only white-space text) is removed, counted as `element:script-empty`, and does not make `runsScripts` true (an outside `<script src>` used to leave an empty `<script>` and a "runs scripts" hold for a page that can run nothing). A script with inline code, or with an allowed `assetPrefix` source, is unchanged.
- **`runsScripts` and `NO_SCRIPT_CSP`.** The result carries `runsScripts: boolean`, read from the sanitised tree: true when a `<script>` element of any type (JSON types such as `application/json` and `application/ld+json` count) or an inline `on*` handler is left in it (`javascript:` URLs never survive). With `allowScripts: false` every `<script>` and every `on*` attribute is removed, so `runsScripts` is always false (and false for the inert page). Serve a page with `runsScripts: false` under `NO_SCRIPT_CSP` = `default-src 'none'; script-src 'none'; style-src 'unsafe-inline'; img-src data: 'self'; sandbox`: no script, inline style only (style attributes and `<style>` are sanitised), images only from `data:` and the page's own origin (the app's `assetPrefix` paths; CSP cannot name a path without a host), nothing else, and a sandbox without any `allow-*` token. It passes `viewerDocumentCspOk`; the app adds its own `frame-ancestors <viewUrl> <publicUrl>`. A page with `runsScripts: true` needs the app's script policy instead.
- **Text slots (`data-tb-text`).** An element with `data-tb-text="key.path"` is kept, and so is the attribute when its value matches `^[a-z][a-z0-9_]*(\.[a-z0-9_]+)*$` (else only the attribute is removed, kind `attribute:data-tb-text`). The sanitiser never fills a slot. The app writes ESCAPED text into the slots AFTER sanitising, with `fillTextSlots(sanitisedHtml, { "key.path": "text" })`: it parses the page, sets each slot's only child to a text node, and serialises, so the serialiser escapes the value (`<img src=x onerror=...>` comes out as visible text, never as markup). A slot on `script`, `style`, `template`, `noscript`, `iframe`, `xmp` or a void element (`img`, `br`, ...), a slot whose key has no value, and a slot with an invalid key are left alone. Do not build slot text by string concatenation.
- **Limits.** This removes static constructs. With `allowScripts: true` a script can still build a link and click it (`a.click()`), so scripts keep the iframe sandbox and the CSP as their only guard; `allowScripts: false` is the only mode where "the page cannot make a request" is a property of the HTML.
- **Tests.** `test/vectors/agent-documents/` holds one `.html` per case and `cases.json` (the corpus; 120+ pages). Fire on bad: every hostile page comes out with no construct the rule list matches and the neutralised strings absent. Quiet on good: the benign pages come back equal except for the marker with nothing removed. Mutation guard (A3): for every hostile case the RAW page must hold at least one construct the rule list matches, and a sanitiser that removes nothing must fail the same checks, so "0 removals" cannot pass by accident. Property: sanitising twice equals sanitising once, and a seeded fuzz of mixed corpus pieces always ends safe. No secret-shaped fixtures.
- **Real-browser canary (required in the apps).** These tests run in Node and prove the rules, not the browser. Live Artifacts (S2) and Creative (S3) keep their real-browser no-egress canary: it must load the RAW hostile page under the real `/_d/` CSP and see canary hits (so the canary is proven to fire), and then load the SANITISED page and see 0. A canary that cannot see the raw page hit proves nothing about the sanitised one.
